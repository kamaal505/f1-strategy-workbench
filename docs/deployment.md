# Streamlit Community Cloud deployment

The public interface defaults to fail-closed mode; set `F1_STRATEGY_MODE=local` only for private local research. A synthetic demonstration is neither authorization for real races nor a real-race launch. Free source availability and code licensing do not grant upstream F1 public-display or redistribution rights. Operator records represent assertions of permission, not a legal determination.

## Prerequisites and setup

1. Obtain applicable rights for every actual source and session, including the complete fitting, tuning and calibration corpus. Prepare server-only authorization records and any authorized model/snapshot artifacts. Do not commit credentials, authorization evidence, private tokens or unauthorized artifacts.
2. Connect the operator-controlled GitHub repository to a Streamlit Community Cloud account with repository administrator access; choose branch `main`, Python 3.12 and entrypoint `streamlit_app.py`. The root `uv.lock` and installable `pyproject.toml` are the only dependency specification. Cloud selects uv; confirm its build log shows the locked project and package installed. If the provider no longer installs the project under this configuration, report that prerequisite instead of adding a startup installer.
3. To enable real sources, set server-side `F1_STRATEGY_AUTHORIZATION_FILE` to a private JSON file containing an array of records with `source_ids`, `session_ids`, `scopes`, `expires_utc` (UTC ISO timestamp or null), `permission_reference_id` and `confirmed_utc` (UTC ISO timestamp). Synthetic-only operation needs no real-source authorization file. Confidential proof stays outside the repository. Each source/session pair and requested scope must be covered by an unexpired confirmed record. Scopes are `source_access`, `snapshot_retention`, `public_display`, `derived_report_download`, `model_server_use` and `public_asset_distribution`. Fitting/tuning/calibration lineage is checked independently of the focal observation; downloads require report permission throughout. Revocation/expiry blocks subsequent returns.
4. Hosted acquisition uses anonymous TracingInsights access; no source login, API key or confirmation environment variables are needed. The parent checks `source_access` and `snapshot_retention` against records for `tracinginsights:YYYY-RR-R` before launching the child and at publication. Workers receive neither credentials nor the authorization-record path. Hosted acquisition is restricted to curated races, without telemetry. Offline replay requires no network.
5. The operator may generate `<root>/public_registry.json` as a JSON array of entries with `session_id`, `snapshot_id`, `model_id`, `driver_number`, `completed_lap`, and optionally a validated `scenario` object. Only `2023-07-R`, `2023-15-R`, `2024-03-R` and clearly labelled synthetic entries are admitted. IDs refer to immutable artifacts beneath the server root, not visitor paths. Each manifest and full lineage must validate, and all required public distribution, display and model-use scopes must be granted before model arrays are loaded. Missing or invalid entries are omitted. A generated synthetic `index.json` in the selected demo root is automatically discovered when its model is available.
6. Run `uv run --locked f1-strategy deployment-check --root <root>`, then inspect the actual Cloud build and test the public URL in a fresh browser. Check an authorized real-race comparison, report download, identity, credential isolation and expiry behavior. An available catalog is not proof of provider installation, permission, public access or successful launch.

`F1_STRATEGY_PUBLIC_ROOT` may select an operator-controlled hosted artifact root. It is server configuration, not a visitor path selector. Without a configured real registry and applicable permissions, retain the packaged labelled synthetic demonstration.

The local 68-race acquisition in `data/free/` is not deployed data. Those files are ignored by Git, and server-use permission alone does not authorize committing snapshots or model weights. Build and validate the required as-of/frozen models locally before registering real entries. See [local workflow](local-workflow.md) and [methodology](methodology.md).

## Capacity and persistence

The parent admits one heavy acquisition, comparison or report-rendering child at a time; concurrent requests get `busy`, with no queue. Admission deadlines are 180 seconds for ingestion and 90 seconds for comparison/report rendering, including validation. Hosted comparisons default to 200 draws and allow at most 1,000. Request stdin is capped at 256 KiB, captured stdout at 8 MiB and stderr at 1 MiB. Report input is limited to 8 MiB; the fixed renderer returns only a relative filename and checksum. Reports use the sealed analysis without loading snapshots/models, and full-lineage download permission is rechecked before return.

The parent monitors files under its root, including staging, snapshots and hosted reports, against 256 MiB every 0.5 seconds. Writes can overshoot between observations; this is not an operating-system disk or memory quota. Workers are terminated and reaped before staging cleanup. Leases protect snapshot readers from eviction. Errors never return stale or fabricated results.

Streamlit Community Cloud can sleep and cold-start, and its filesystem is ephemeral. Store only appropriately authorized deployable artifacts in the repository; no persistent hosted storage is assumed. Cloud may override server security settings. The bounds above are configuration limits, not measured Cloud performance promises. Measure installation, wall time, cache peak and termination on the target deployment; do not silently reduce a valid analysis’s statistical semantics to fit capacity. The repository is available; remaining launch gates are connected-account consent, applicable rights, ready real models and successful provider/public-browser proof.
